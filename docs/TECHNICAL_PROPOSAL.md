# 기술 제안서 — Festival 공시 Agent

제10회 2026 미래에셋증권 AI Festival · 공시 Agent

---

## 1. 제안 요약

DART 전자공시 원문을 구조 보존 방식으로 파싱·청킹해 PostgreSQL 16 + pgvector에 적재하고,
hybrid retrieval과 **결정적(deterministic) 추론**으로 근거가 붙은 답변을 먼저 확정한 뒤,
HyperCLOVA X는 그 확정된 문장을 다듬는 역할만 맡습니다.

> **언어모델이 틀릴 수 있는 지점을 전부 제거하고, 남은 곳에만 언어모델을 쓴다.**

사실·수치·인용은 전부 결정적 계층이 만듭니다. 언어모델에는 검색된 원문도, 숫자도, 인용도
전달하지 않습니다. 검증에 실패하면 언제나 결정적 답변이 그대로 나갑니다.

| 항목 | 값 |
|---|---|
| 대상 기업 | 70개사 |
| 공시 문서 | 4,204건 (정기 1,054 · 주요 598 · 거래소 1,469 · 지분 1,083) |
| 청크 | 1,363,336개 |
| 저장소 | PostgreSQL 16 + pgvector (HNSW, cosine, 1024차원) |
| 검색 | lexical Top-50 + vector Top-50 → RRF(k=60) → 결정적 rerank → Top-10 |
| 생성 | 결정적 answer generator + HyperCLOVA X(HCX-005) verbalizer |
| API | FastAPI, `GET /healthz`, `GET /answer` |

## 2. 문제 정의

공시 질의응답에서 실패는 "답을 못 찾는 것"보다 **"틀린 답을 자신 있게 말하는 것"** 이
치명적입니다. 투자 판단의 근거가 되는 수치이기 때문입니다.

일반적인 RAG 구성에서 이 실패가 생기는 지점은 넷입니다.

```
① 원문 해석      모델이 검색된 표·문장을 읽고 수치를 재구성한다
                 → 단위·기간·연결/별도 기준을 섞는다

② 수치 생성      모델이 문맥에서 그럴듯한 숫자를 만든다
                 → 검증할 방법이 없다

③ 인용 조작      모델이 [1] 같은 마커를 스스로 붙인다
                 → 인용이 실제 근거를 가리키지 않는다

④ 존재 판단      모델이 "답할 수 있는지"를 스스로 결정한다
                 → 근거가 없어도 답을 만든다
```

여기에 공시 도메인 고유의 어려움이 더해집니다.

- **정정 공시** — 원본과 정정본이 공존하고, 어느 쪽이 최신인지 검색 순위로는 알 수 없습니다.
- **이벤트 생명주기** — 계약 체결과 해지가 별개 문서로 존재하고, 한쪽만 검색되면 답이 뒤집힙니다.
- **역할 충돌** — 지분공시에는 보고자와 발행회사가 함께 등장해, 둘을 뒤바꾸면 정반대 답이 됩니다.
- **구조 손실** — 표를 평문으로 만들면 행·열의 의미가 사라지고, 병합 셀은 복원 불가능해집니다.

## 3. 제안 방법

### 3.1 원칙에서 파생된 규칙 다섯 개

| 규칙 | 막는 실패 |
|---|---|
| 모델은 검색된 원문을 보지 않는다 | ① 원문 해석 |
| 모델은 숫자를 보지 않는다 (placeholder 마스킹) | ② 수치 생성 |
| 모델은 인용을 만들지 않는다 (분리 후 결정적 재부착) | ③ 인용 조작 |
| 모델은 답의 존재 여부를 판단하지 않는다 | ④ 존재 판단 |
| 검색 랭킹이 근거 완전성을 결정하지 않는다 | 정정·생명주기 누락 |

### 3.2 구조 보존 청킹

고정 길이로 자르지 않고 문서 구조를 따릅니다.

```
본문   section → paragraph → sentence → chunk
표     병합 셀을 논리 그리드로 복원 → header → row group
       (행을 문자 길이로 자르지 않음. 모든 묶음에 header와 표 context를 반복)
공시   유형별 독립 전략 (정기 / 주요·거래소 / 지분)
추적   결정적 chunk ID + 문서·section·table provenance + 앞뒤 chunk 링크
```

검색 문맥은 원문 `content`와 별도로, 기업·공시·section 경로를 담은 `retrieval_text`를
따로 만듭니다.

### 3.3 근거 완전성 — 랭킹에 맡기지 않는 부분

검색 순위는 관련도를 정렬할 뿐, "빠진 문서가 없다"를 보장하지 못합니다. 그래서 랭킹과
**독립적인 결정적 경로**를 둡니다.

```
정정 그래프        정정 관계를 결정적 규칙으로 사전 구축
                   → 질의 기간이 배제한 원본까지 되찾음

이벤트 타임라인    계약 ↔ 해지 생명주기를 사전 연결
                   → 해지만 검색돼도 원 계약을 되찾음

다중문서 완전성    열거형 질의에서 기대 슬롯을 먼저 정의하고 채움

필터 완화          라우팅이 후보를 전멸시킨 경우에만, 추론된 메타데이터만 양보
                   (기업·공시유형·기간은 절대 완화하지 않음)
```

**전부 랭킹 이후에 덧붙이므로 검색 순서를 바꾸지 않습니다.**

### 3.4 HyperCLOVA X 안전 봉투

```
결정적 답변   "2024-03-14에 1,234,567주로 변동 [1]"
      │
      ├─ 인용 분리 ─────────────► [1] 은 모델에 전달되지 않음
      ▼
값 마스킹     "{{DATE_1}}에 {{NUM_1}}로 변동"    숫자 0개 · 인용 0개
      ▼
HCX-005 (temperature=0, 단일 이벤트 claim만)
      ▼
검증 게이트 — 하나라도 걸리면 즉시 결정적 답변으로 복귀
   placeholder 무결성 · 모델이 만든 인용 · placeholder 밖 숫자 생성
   · 구조화 TEXT 재생성 · 단위 중복 · 투자 권유 표현 · 추론 문장 · 사실 검증기
      ▼
인용 재부착 (이벤트 소유권 기준, 결정적)
      ▼
최종 답변
```

값이 왕복을 **통과하거나 실패할 뿐, 조용히 바뀔 수 없습니다.** 부분 복구나 추정 수정은
하지 않습니다.

**모델에 원문이 전달되지 않는다는 것은 프롬프트 인젝션 경로가 구조적으로 없다는 뜻이기도
합니다.** 공시 원문에 어떤 문자열이 들어 있어도 모델 입력에 도달하지 않습니다.

### 3.5 대회 규칙 준수

| 규칙 | 준수 방식 |
|---|---|
| 제공 코퍼스 외 데이터 사용 불가 | 서빙 경로에 외부 호출이 없음. 근거는 DB의 청크뿐 |
| 외부 공시 API 실시간 호출 불가 | 파싱·적재는 오프라인 1회. 요청 처리 중 코퍼스를 다시 읽지 않음 |
| 근거 없는 예측·투자 의견 금지 | 투자 권유·전망 표현 검증기. 걸리면 결정적 답변으로 복귀 |
| 확인 불가 시 명시 | 5-state 질의 게이트 + 답변 가능성 판정 → 한계 고지 또는 역질문 |
| 모든 답변에 근거 공시 표시 | 모든 사실 문장이 chunk와 `source_refs`까지 추적되는 인용을 가짐 |

## 4. 시스템 구성도 · 주요 기능 흐름도

상세는 [`docs/architecture/SERVING_ARCHITECTURE.md`](architecture/SERVING_ARCHITECTURE.md)에
있습니다. 한 장에 한 가지 분류 기준만 담아 네 개 관점으로 나눴습니다.

| 관점 | 답하는 질문 |
|---|---|
| 평면 | 무엇이 언제 도는가 (오프라인 / 질의 / 실행) |
| 관문 | 요청이 어디서 끝날 수 있는가 (종료 지점 3개) |
| 레인 | 질문 유형에 따라 무엇이 달라지는가 |
| 방어선 | 평가 기준 각각을 무엇이 막고 있는가 |

요약하면 다음과 같습니다.

```
질문
  │
  ▼
질의 이해 · 검증 ──── 미해결 ──→ 역질문 / 범위 밖 고지          (종료 ①)
  │ 해결
  ▼
Hybrid Retrieval      lexical + vector → RRF → 결정적 rerank
  │                   + 정정 그래프 · 이벤트 그래프 · 완전성 보강
  ▼
레인별 추론           지분 / 정기 / 기업이벤트 / 일반근거 / 계약금액 비교
  │
  ▼
결정적 답변 생성      ★ 정답의 기준선. 이후 단계는 이를 넘어설 수 없음
  │
  ▼
답변 가능성 판정 ──── 근거 부족 ──→ 한계 고지                    (종료 ②)
  │ 가능
  ▼
HCX 안전 봉투 ────── 검증 실패 ──→ 결정적 답변 그대로            (종료 ③)
  │ 통과
  ▼
question_id · question · retrieved_context · think_trace · answer
```

## 5. 사용자 시나리오

### 5.1 단일 사실 조회

```
질문   "삼성전자의 2025년 연결기준 매출액은 얼마인가?"

경로   query_understanding → query_validation → task_router
       → evidence_builder → periodic_fact_resolver
       → periodic_evidence_selector → answer_composer
       → answer_generator → answerability_guard

답변   2025년 사업보고서 연결 손익계산서의 매출액 행 + 인용
```

### 5.2 복합 문서 추론 — 계약 이후 해지

```
질문   "한화오션이 2025년에 체결한 주요 계약 이후 해지된 계약이 존재하는가?"

경로   multi_document_planner → multi_document_executor
       → multi_document_evidence → contract_lifecycle_resolver

핵심   해지 공시만 검색돼도 이벤트 그래프가 원 계약을 되찾습니다.
       근거가 없으면 "없습니다"라고 단정하며, 이는 추측이 아니라
       그래프가 연결을 찾지 못했다는 결정적 사실입니다.
```

### 5.3 답할 수 없는 질문

```
질문   "그 회사 공급계약 알려줘"          → 기업이 특정되지 않음
답변   "어느 회사에 대한 공시를 확인할까요?"

질문   "2027년 실적 전망은?"              → 코퍼스 범위 밖
답변   "현재 제공된 공시 데이터 범위에서는 확인할 수 없습니다."
```

**무리한 답변 대신 한계를 고지하거나 필요한 정보를 역질문합니다.** 이것이 실패가 아니라
설계된 동작입니다.

### 5.4 실행 경로의 자체 보고

모든 응답에 `think_trace`가 실려 나갑니다. 어떤 컴포넌트가 실행됐고 무엇으로 결론 났는지가
기록되므로, **"왜 이 답이 나왔는가"를 응답만 보고 재구성할 수 있습니다.**

```json
{
  "task_type": "periodic_fact",
  "route": "periodic_fact_resolver",
  "stages": ["query_understanding", "query_validation", "task_router", "..."],
  "retrieval_count": 10,
  "selected_evidence_count": 10,
  "answerable": true,
  "warnings": ["multiple_temporal_alternatives"],
  "hcx_status": "success"
}
```

chain-of-thought가 아닙니다. 컴포넌트 이름·개수·상태값만 담기며, 모델의 내부 추론 텍스트는
포함되지 않습니다.

## 7. 확장성

### 7.1 확장 비용의 형태

새 공시 유형을 추가하는 비용은 파이프라인 수정이 아니라 **레인 하나 구현**입니다.

```
레인 계약   prepare → resolve → compose

지분공시    prepare 4단계 (원본이 가장 불규칙)
정기공시    prepare 0단계
기업이벤트  prepare 0단계
```

지분공시 레인이 깊은 것은 그 유형의 원본이 가장 불규칙하기 때문입니다 — 변동전/후 이중
표기, 보고자와 발행회사의 역할 충돌, 정정 체인, 동일 사건의 복수 뷰. **구조가 가장 어려운
유형을 먼저 완결시켜 결정적 추론이 실제 공시 데이터에서 가능함을 증명했고**, 그 과정에서
얻은 것은 지분공시 전용 코드가 아니라 재사용 가능한 레인 계약입니다.

### 7.2 다중 기업 비교

비교는 하나의 질의가 아니라 **N개의 단일 기업 질의 + 결정적 결합**으로 실행됩니다. 한 번의
랭킹에 여러 기업을 넣으면 매칭이 잘 되는 기업이 결과를 독식하기 때문입니다.

```
"A와 B의 계약금액 비교"
        │
   ┌────┴────┐
   ▼         ▼
 A만의     B만의        각각 기존 검색·추론을 그대로 사용
 질의      질의
   │         │
   ▼         ▼
 피연산자  피연산자
   └────┬────┘
        ▼
   결정적 비교          숫자 비교. 모델 개입 없음
```

현재는 **피연산자를 확정적으로 추출할 수 있는 계약금액에 한정**해 실행합니다. 거래소공시
단일판매·공급계약은 계약금액을 항상 같은 필드·같은 단위로 기재하므로 비교가 성립합니다.

반면 서술형 금액은 그렇지 않습니다.

```
LG에너지솔루션   "2025년 당기 중 총 10.5조원"
삼성SDI          "2025년 상반기 중 1조 8,430억원"
                  └ 기간(당기/상반기)도 기준도 다름
```

이런 값을 억지로 비교하면 **틀린 순위를 확신 있게 말하는** 최악의 실패가 됩니다. 그래서
추출이 보장되지 않는 필드는 **실행하지 않고 한계를 고지합니다.**

### 7.3 다음 단계

현재 미구현 항목 두 가지는 **하나의 빠진 조각을 공유합니다** — 서술형 본문과 표에서
(지표, 값, 단위, 기간)을 결정적으로 추출하는 계층입니다.

| 미구현 | 막힌 이유 |
|---|---|
| 정기공시 답변의 자연어 문장화 | 값은 있으나 단위가 텍스트 밖에 있어, 단정하면 자릿수 오류 위험 |
| 계약금액 외 필드의 기업 비교 | 피연산자를 같은 기준으로 뽑을 수 없음 |

이 추출 계층이 갖춰지면 두 항목이 동시에 열립니다. 그리고 **그 전까지는 실행하지 않는 것이
설계 의도입니다** — 확신 있는 오답보다 정직한 한계 고지가 낫다는 것이 이 시스템의 일관된
선택입니다.

### 7.4 운영 확장

```
모델 교체        임베딩 테이블이 청크와 분리되어 있고
                 (chunk_id, model, version)이 기본키
                 → chunk ID·본문·provenance를 유지한 채 교체·병행 가능

코퍼스 확장      파서·청커가 공시 유형별 독립 전략
                 → 새 유형은 전략 하나 추가

배포             Dockerfile 단일 이미지. 검색 데이터는 이미지가 아닌 DB에 있어
                 이미지에는 코퍼스 메타데이터만 포함 (14.16GB → 6.26MB)
```

## 8. 한계와 리스크 관리

정직하게 기록합니다. 아는 한계를 밝히는 것이 신뢰 가능한 서비스의 조건이라고 봅니다.

| 한계 | 현재 대응 |
|---|---|
| 정기공시 검색 성능이 가장 낮음 (R@1 0.29) | 측정으로 확인. 내부 회귀 세트가 지분공시에 편중되었던 결과 |
| 정기공시 답변이 구조화 근거 나열 형태 | 사실과 인용은 정확하나 문장으로 정리되지 않음. §7.3 참조 |
| 계약금액 외 기업 비교 미지원 | 실행하지 않고 한계 고지 |
| 자연어 문장화가 지분공시 레인에서만 동작 | 나머지 유형은 결정적 답변을 그대로 서빙 |

**모든 한계에서 시스템은 "모른다고 말하는" 쪽을 선택합니다.** 근거가 없거나 확신할 수 없을
때 답을 만들지 않는 것이, 이 도메인에서 가장 중요한 안전 속성이라고 판단했습니다.
