# 개발 대원칙

2026-09-04 정리. 일반론이 아니라 **이 저장소에서 실제로 산으로 갔던 지점들**에서 뽑았습니다.
각 원칙 아래에 그날 무슨 일이 있었는지 적어 두었으니, 같은 우회로를 반복하지 마십시오.

---

## 1. 저장소가 이미 답을 갖고 있는지 먼저 본다

```
pipeline.py·orchestrator.py 재구성을 제안 → 철회
  FREEZE_LOG가 "cleanup·restructuring 목적의 재개봉 금지"를 명시하고 있었음

비교 계층을 새로 구현 → 되돌림
  dev에 company_comparison.py 721줄 + 테스트 1,127줄이 이미 있었음
  게다가 기존 구현이 더 나았음(검색 결과 수준 병합 → 하류 전부 통과)
```

**새로 만들기 전에 `git grep`, `git branch -a`, `docs/FREEZE_LOG.md`.**
이 저장소는 결정과 근거가 문서로 남아 있습니다. "왜 이렇게 돼 있지?"의 답이 대개 이미 있습니다.

## 2. 테스트가 이름으로 금지하는 건 실수가 아니라 결정이다

```
_comparison_from_query 확장 → 테스트 17개 실패

  test_a_frame_does_not_make_a_question_an_executable_comparison
  test_a_frame_does_not_make_a_comparison_answerable
  test_a_cross_company_frame_blocks_role_reinterpretation
```

이름 자체가 하지 말라고 말하고 있었고, `_comparison_frame`의 독스트링에도
"firewall signal, not an execution signal"이라고 적혀 있었습니다.

**테스트가 깨지면 "고쳐야 할 테스트"가 아니라 "내가 몰랐던 계약"을 먼저 의심합니다.**

## 3. 막힌 이유를 측정하기 전에 해결책을 정하지 않는다

```
정기공시 문장화를 "어렵다 → 쉽다 → 불가능"으로 세 번 뒤집음

실제로 필요했던 것은 쿼리 두 개:
  정기공시 표의 단위 보유율        42.5%
  섹션 본문에서 회수 가능한 비율     2.3%
```

30초면 결론이 났을 것을 몇 시간 논의했습니다.

**"할 수 있나?"는 추론이 아니라 측정으로 답합니다.**

## 4. 안전망이 실제로 그 변경을 잡는지 확인한다

```
"trace 기록화는 기존 테스트가 검증해 준다"고 판단 → 틀렸음
  think_trace를 검증하는 테스트 13개가 전부 assertIn(멤버십)
  순서를 보는 테스트는 하나도 없었음
  → 순서를 깨뜨려도 전부 통과했을 것
```

**"테스트가 있으니 안전하다"가 아니라, "이 테스트가 이 변경의 이 실패를 잡는가"를 봅니다.**
안 잡으면 변경 전에 잡는 테스트를 먼저 만듭니다.

## 5. 추가로 되는 일을 수정으로 하지 않는다

오늘 성공한 변경들의 공통점입니다.

```
필터 완화(OF4)     strict-zero 일 때만 동작
                   → 지금 검색되는 질문은 이 코드에 도달조차 하지 않음

비교 1단계(OF3)    검증 차단 지점에서 분기
                   → 방화벽을 뚫지 않고 옆에 문을 냄

비교 2단계         게이트 실패 시 1단계 실행 객체를 그대로 반환
                   → 실패의 최악이 "직전 동작"
```

**변경의 최악이 "현재 동작"이 되도록 설계합니다.** 그러면 배포 판단이 쉬워지고,
회귀가 나도 잃는 것이 없습니다.

## 제품 원칙과 같은 말입니다

이 시스템이 답변에 대해 지키는 원칙이 개발에도 그대로 적용됩니다.

> **확신 있는 오답보다 정직한 한계 고지가 낫다.**

| 제품 | 개발 |
|---|---|
| 근거가 없으면 답을 만들지 않는다 | 측정하지 않았으면 "된다"고 말하지 않는다 |
| 검증 실패 시 결정적 답변으로 되돌아간다 | 게이트 실패 시 기존 동작으로 되돌아간다 |
| 추출이 보장되지 않으면 실행하지 않는다 | 안전망이 없으면 변경하지 않는다 |
| 모델은 원문·숫자·인용을 보지 않는다 | 변경은 자기가 건드릴 것만 본다 |

## 변경 전 체크리스트

```
[ ] 같은 일을 하는 코드가 이미 있는가          git grep · git branch -a
[ ] FREEZE_LOG가 이 파일을 지목하는가          동결이면 재개봉 절차 필요
[ ] 이 변경이 깨뜨릴 계약을 아는가             테스트 이름과 독스트링을 읽는다
[ ] 이 변경의 실패를 잡는 테스트가 있는가       없으면 먼저 만든다
[ ] 실패했을 때 무엇이 남는가                  "현재 동작"이 아니면 재설계
[ ] 측정으로 확인했는가                        추론으로 결론 내지 않는다
```

## 테스트 실행 규칙

```bash
FESTIVAL_HCX_ENABLED=false python -m pytest tests/ -q
```

`.env`를 소스한 셸에서 그냥 돌리면 **실제 HCX API가 호출됩니다.** 비용이 들고, 같은 테스트가
실행마다 달라지며, 결정적 답변을 기대하는 테스트가 문장화된 답변을 받아 실패합니다.
그건 코드 회귀가 아닙니다.
