# Festival 공시 Agent — 시스템 구조

이 문서는 저장소의 현재 구현(`dev`)을 기준으로 작성했습니다. 그림은 **한 장에 한 가지
분류 기준만** 담습니다. 실행 순서와 종료 조건과 질문 유형을 한 그림에 섞으면 어느 것도
읽히지 않기 때문입니다.

| 그림 | 답하는 질문 |
|---|---|
| A · 평면 | 무엇이 언제 도는가 |
| B · 관문 | 요청이 어디서 끝날 수 있는가 |
| C · 레인 | 질문 유형에 따라 무엇이 달라지는가 |
| D · 방어선 | 평가 기준 각각을 무엇이 막고 있는가 |

---

## 0. 설계 기준

> **언어모델이 틀릴 수 있는 지점을 전부 제거하고, 남은 곳에만 언어모델을 쓴다.**

이 한 문장에서 나머지가 파생됩니다.

```
규칙 1   모델은 검색된 원문을 보지 않는다
규칙 2   모델은 숫자를 보지 않는다          (placeholder로 가려서 전달)
규칙 3   모델은 인용을 만들지 않는다        (호출 전 분리 → 결정적 재부착)
규칙 4   모델은 답의 존재 여부를 판단하지 않는다
규칙 5   검색 랭킹이 근거 완전성을 결정하지 않는다
```

사실·수치·인용은 전부 결정적 계층이 만들고, HyperCLOVA X는 **이미 검증된 문장을 다듬는
역할만** 맡습니다. 검증에 실패하면 언제나 결정적 답변이 그대로 나갑니다.

## 3. 그림 C · 레인 — 질문 유형에 따라 무엇이 달라지는가


**레인마다 깊이가 다릅니다.** 지분공시는 원본이 가장 불규칙해서(변동전/후 이중 표기,
보고자와 발행회사의 역할 충돌, 정정 체인, 동일 사건의 복수 뷰) 전처리가 4단계이고,
정기공시는 0단계입니다.

이것이 확장 비용의 형태입니다 — 새 공시 유형을 추가하는 비용은 파이프라인 수정이 아니라
**레인 하나 구현**입니다.

### 기업 비교 레인의 실행 조건

비교는 하나의 질의가 아니라 **N개의 단일 기업 질의 + 결정적 결합**으로 실행됩니다.
한 번의 랭킹에 여러 기업을 넣으면 매칭이 잘 되는 기업이 결과를 독식하기 때문입니다.

```
"A와 B의 계약금액 비교"
        │
   ┌────┴────┐
   ▼         ▼
 A만의     B만의        각각 기존 검색·추론을 그대로 사용
 질의      질의
   │         │
   ▼         ▼
 피연산자  피연산자
   └────┬────┘
        ▼
   결정적 결합       숫자 비교. 모델 개입 없음
```

실행은 **모든 조건이 갖춰졌을 때만** 허용됩니다.

| 조건 | 미충족 시 |
|---|---|
| 기업이 2개 이상 명시됨 | 실행하지 않음 |
| 모든 기업이 코퍼스 코드로 해결됨 | 실행하지 않음 |
| 기업마다 자기 피연산자를 가짐 | 실행하지 않음 |
| 요청 필드가 이 레인이 비교하는 필드임 (현재: 계약금액) | 실행하지 않음 |

**피연산자를 확정적으로 추출할 수 없는 필드는 실행하지 않고 한계를 고지합니다.** 단위·기준
기간·연결/별도 기준이 제각각인 값을 억지로 비교하면, 틀린 순위를 확신 있게 말하는 최악의
실패가 됩니다. 필드 확장이 다음 단계입니다.

## 4. 표 D · 방어선 — 평가 기준 각각을 무엇이 막고 있는가

| 평가지표 | 방어 | 구현 |
|---|---|---|
| **근거 기반**(환각) | 모델은 검색 원문을 보지 않는다 | HCX 프롬프트에 원문 미전달 |
| | 모델은 숫자를 보지 않는다 | `{{DATE_1}}` `{{NUM_1}}` placeholder 마스킹 |
| **안전성·신뢰성** | 모델 입력에 외부 텍스트가 없다 | 프롬프트 인젝션 경로 부재 |
| | 투자 권유·전망 표현은 폐기 | 금지 표현 검증 → fallback |
| **정확성** | 수치는 결정적 resolver가 확정 | holding / periodic resolver |
| | 모델은 그 값을 바꿀 수 없다 | placeholder 왕복 무결성 검사 |
| **근거 완전성** | 랭킹이 완전성을 결정하지 않는다 | 정정 그래프 · 이벤트 그래프 · 다중문서 보강 |
| **근거 표시** | 모델은 인용을 만들지 않는다 | 호출 전 분리 → 이벤트 소유권 기준 결정적 재부착 |
| **정보한계 대응** | 모델이 답의 존재를 판단하지 않는다 | 5-state 질의 게이트 |
| | 못 풀면 역질문한다 | clarification resolver |
| | 근거가 부족하면 그렇게 말한다 | answerability guard |
| **추론 논리성** | 시스템이 실행 경로를 스스로 보고한다 | `think_trace.stages` |

### HCX 안전 봉투

```
결정적 답변   "2024-03-14에 1,234,567주로 변동 [1]"
      │
      ├─ 인용 분리 ─────────────────► [1] 은 모델에 전달되지 않음
      │
      ▼
값 마스킹     "{{DATE_1}}에 {{NUM_1}}로 변동"     숫자 0개 · 인용 0개
      │
      ▼
HCX-005 (temperature=0, 단일 이벤트 claim만)
      │
      ▼
검증 게이트 — 하나라도 걸리면 즉시 결정적 답변으로 복귀
      ├ placeholder 무결성 (누락·중복·순서변경·미지토큰)
      ├ 모델이 만든 인용 마커
      ├ placeholder 밖 숫자 생성
      ├ 구조화 TEXT 값 재생성
      ├ 단위 중복
      ├ 투자 권유·전망 표현
      ├ 추론·결론 문장 추가
      └ 사실 검증기
      │
      ▼
인용 재부착 (이벤트 소유권 기준, 결정적)
      │
      ▼
최종 답변
```

값이 왕복을 **통과하거나 실패할 뿐, 조용히 바뀔 수 없는** 구조입니다. 부분 복구나 추정
수정은 하지 않습니다.

## 부록 A · 실행 단계 어휘

어떤 질문이 어떤 경로를 탔는지 응답만 보고 재구성할 수 있습니다.

```
            holding_evidence_coverage · holding_date_intent

            periodic_fact_resolver · periodic_evidence_selector
```

## 부록 B · 저장 스키마

```
companies ─ disclosures ─ sections ─ disclosure_tables
                  └─ chunks ─ chunk_source_refs
                        └─ chunk_embeddings   (HNSW cosine, 1024차원)

correction_relations / correction_group_members        (db/006)
corporate_events / _members / _relations               (db/007)
```

임베딩은 청크와 **분리된 테이블**입니다. 모델을 교체해도 chunk ID·본문·provenance는
그대로 유지되며, `(chunk_id, embedding_model, embedding_version)`이 기본키라 여러 모델을
동시에 보관할 수 있습니다.

## 부록 C · 검색 구성

| 파라미터 | 값 |
|---|---|
| 최종 top_k | 10 |
| lexical top_n / vector top_n | 50 / 50 |
| RRF k | 60 |
| fusion / deterministic 가중치 | 0.60 / 0.40 |
| 임베딩 | bge-m3, 1024차원, HNSW cosine |

내부 회귀 세트(지분공시 22문항) 측정값입니다.

| | R@1 | R@3 | R@5 | R@10 | MRR |
|---|---|---|---|---|---|
| lexical 단독 | 0.318 | 0.455 | 0.545 | 0.591 | 0.415 |
| vector 단독 | 0.273 | 0.545 | 0.636 | 0.727 | 0.445 |
| **hybrid** | **0.409** | **0.727** | **0.727** | **0.864** | **0.554** |

하이브리드가 lexical 단독 대비 R@3에서 60%, R@10에서 46% 높습니다. 벡터 레인이 실제로
기여하고 있음을 같은 실행 안에서 측정한 값입니다.

## 부록 D · 응답 계약

최상위는 **정확히 5개 필드**입니다.

| 필드 | 설명 |
|---|---|
| `question_id` | 요청 값 그대로 |
| `question` | 요청 값 그대로 |
| `retrieved_context` | 서빙된 Top-K 청크 (rank · chunk_id · doc_id · provenance 등) |
| `think_trace` | 실행 요약 — 컴포넌트 이름·개수·상태값만. 모델의 내부 사고는 담기지 않음 |
| `answer` | 최종 답변. 어떤 경우에도 빈 문자열이 아님 |
